Research design • 13 October 2026 UTC • CPU-validated reference rules; GPU performance remains unmeasured

A complete tablebase solver that can start on one H100 and grow across a GPU fleet

The proposed core is a factorized legal-move operator over packed state, executed inside dependency-ordered, independently checkpointed shards. Use segmented bit operations for ordinary moves and exact floating-point reductions where shared relations make tensor cores economical.

Scope: this is an algorithm design and correctness research package, not a finished production generator or a generated nine-piece database. The code validates finite-graph WDL, bounded floating-point predicates, toy clocked dynamic programs, and actual chess quiet-move relations. There is no CUDA GPU in the execution environment.

2. Public nine-piece progress

Lichess's 7 February 2026 announcement makes a precise nine-piece claim: Marc Bourzutschky has computed selected op2 configurations containing two opposing pawn pairs and no additional pawns. Any capture leads into an eight-piece op1 position. The post shows nine-piece examples from Carlsen–Aronian and Adams–Stefansson.

The publicly released eight-piece op1 set is 63 TiB, covers approximately 5 × 1014 legal positions, and uses DTC rather than Syzygy's DTZ50 metric. Op1/op2 exploit closure under quiet moves and captures into solved smaller sets. This is real restricted nine-piece coverage, not a complete nine-piece tablebase. The research search did not locate a credible public claim of a complete unrestricted nine-piece collection.

For our target, these techniques can supply early milestones and dependency oracles, but cannot justify excluding other nine-piece material or placements.

3. Define the exact target

Generate complete material closure: all legal moves, captures, queen/rook/bishop/knight promotions, pawn double pushes, en passant and supported castling-right states. Enumerated index slots may include illegal placements; every such slot has an explicit validity predicate or mask. No heuristic pruning is permitted to remove an unsolved valid position.

Separate (a) unclocked WDL/DTM, (b) a specified tablebase fifty-move model, and (c) strict FIDE clock claims. These have different values and should carry distinct format metadata. The common automatic-100-ply model is not identical to optional FIDE draw claims. FIDE allows fifty-move claims and an automatic seventy-five-move draw, with checkmate taking precedence. An exact clock-claim operator adds a draw action when claimable and uses the 150-ply automatic boundary. Arbitrary prior repetition history is not determined by board, rights and halfmove clock alone; a history-aware probing engine must supply it, or a separate history-state solver is required.

The prototype tests both the automatic-clock model and a toy optional-claim/automatic-deadline model. It does not implement a complete chess repetition-history graph. See FIDE rules and the formal model in ChessTB's correctness document.

4. Dependency order turns the clocked core into a DAG

potential(position) = (piece_count,
                       total remaining pawn advances to promotion,
                       number of retained castling rights)

Capture, pawn move, promotion or loss of rights: decreases potential.
Other quiet moves: same potential, same pawn placement and rights.

Clocked state: (position, halfmove_clock)
Quiet move: clock increases.
Zeroing move: clock resets, but potential decreases.

The pair (potential, remaining time to automatic draw) decreases along every nonterminal transition, so the defined clocked game is acyclic. Solve smaller potential first, then each layer from the deadline clock down to zero. This replaces convergence at an unbounded mate depth with a bounded clock dynamic program. Castling exits decrease rights without resetting the clock and must keep that distinction.

For WDL alone, outcomes at successive clocks often admit a decisive/draw threshold under the chosen semantics. A streaming implementation need hold only the current and next clock planes; outputs can be encoded losslessly as change points. Do not assume arbitrary distance functions have one threshold: exact mate distances may have many changes.

Unclocked WDL and long DTM still require the attractor/fixed-point stage. If cursed wins and blessed losses are output, that stage cannot be omitted merely because the clocked phase finishes. A complete metric package comprises separately defined and verified stages.

5. Factorized move groups

Fix every piece except one nonking piece and vary its square across up to 64 cells. Read the opposite-side-to-move W/L values for those cells as packed words. For quiet moves, the legal relation factors into source validity, movement geometry through fixed blockers, and a destination-only own-king-safety mask.

For rook, bishop and queen moves, fixed blockers split ranks, files and diagonals into segments. All distinct empty squares in the same permitted segment are mutually reachable. Evaluate losing-child existence and nonwinning-child existence by masked segment reductions, excluding the source square. One operation reuses occupancy and legality across many placements and avoids decoding/ranking each successor independently.

Knights use a fixed jump stencil and legality masks. Kings use a separate attacked-square operator and canonical king-slice mappings. Captures, pawn moves, castling and promotions are boundary operations rather than being silently folded into the slider kernel. Identical pieces require canonical set indexing; temporarily expanding a tile into labelled square groups is safe only if each result maps back exactly and duplicate orbit updates are combined.

Validated: 160 actual chess groups, 7,426 legal source rows and 48,842 quiet edges matched python-chess. Of these, 5,369 source rows were sliding-piece cases whose segmented relation matched the legal-move relation exactly. This establishes those sampled local identities, not exhaustive production indexing correctness.

6. Exact floating-point optimization

Let L(y) indicate a losing child and W(y) a winning child. For a reduction with at most 64 destinations, encode:

E(y) = 65 * (1 - W(y)) + L(y)
       = 0 for a winning child
       = 65 for an unresolved/drawn child
       = 66 for a losing child

z(x) = sum_y legal(x,y) * E(y)
     = 65 * nonwinning_count + losing_count

any losing child      <=> z % 65 != 0
all children winning  <=> z == 0, and legal degree > 0

Inputs 0, 1, 65 and 66 are exactly representable in FP16 and BF16. A bounded sum is at most 4,224, so FP32 accumulation represents every possible sum exactly. Decode each bounded reduction before combining flags across larger groups: summing encoded results first can introduce a radix carry and hide losing children. The test suite includes that regression.

Store permanent state as bits; unpack only an active tile into FP16/BF16, compute and immediately repack. Do not store the entire table in floating point. FP8 cannot directly represent this 65/66 encoding, so it needs a different proven encoding or separate binary queries. Also, NVIDIA documents a reduced-precision implementation detail for some FP8 WGMMA accumulation modes. Validate the actual chosen instruction path rather than infer exactness from an FP32 output dtype.

FP16 matrix rows need 128 bytes of adjacency per 64-destination query; packed bitset rows need only 8. Without reuse, a tensor-core formulation can lose on memory and packing even when arithmetic is fast. Native tile padding is another cost: a single useful query column does not fully use a 16-column dot tile. Group relations only when they are genuinely identical and multiple useful state vectors share them. The included GPU benchmark reports queries=1 and queries=16 separately.

NVIDIA PTX ISA specifies FP16/BF16 accumulation precision. The bounded-integer exactness argument is our inference from those semantics. The CPU reference emulates FP16 operands with FP32 accumulation; actual tensor-core behavior and speed remain to be tested on hardware.

7. Shards that survive retries and scale beyond one machine

  1. Deterministic ownership. Use a shard key containing rule/format version, material, pawn placement, rights state, king slice and remaining coordinate range. Split ranges to a memory target rather than assuming every material has uniform size.
  2. Move-aware cache. Prefer neighbouring king/pawn/anchor slices. Stream one boundary input at a time, accumulate proof flags, and retain hot pages during a local closure. Measure useful bytes and misses per proved state.
  3. Adaptive work representation. Sparse sorted IDs for small deltas, runs/compressed bitmaps for clustered deltas, raw bitmaps for dense deltas. A 64-bit ID list crosses the raw two-bit-plane payload size near 3.1% density, before list headers and routing costs.
  4. Idempotent updates. Send proved value bits and dirty notifications. OR combines duplicate proofs safely. Do not use unguarded counter decrements on at-least-once delivery. A loss proof must check all legal successors against valid child values, not infer that a queue looks empty.
  5. Safe commit. Write new immutable blocks and their checksums, then conditionally advance the owner manifest generation. Record dependencies, rule version, input hashes and outstanding epochs. Failed/stale workers cannot overwrite a newer result. Object-store atomic conditional writes or a transactional control database are required.
  6. Termination. Clocked DAG layers finish only after all their input dependencies and assigned ranges are committed. Fixed-point layers finish only after all shards, outbound/inbound messages, dirty sets and in-flight leases are drained by a real distributed termination protocol.
  7. Distance and verification. Keep clocked DP values and unclocked proof ranks distinct. Asynchronous WDL discovery order is not DTM. Use ordered waves or a separate exact distance relaxation, then verify coverage and certificates before publishing table files.

The CPU asynchronous model handled delayed, duplicate notifications across 1, 2 and 7 simulated owners and matched an independent counter-based oracle. It models globally visible values; it does not benchmark a real network or implement the production commit protocol.

9. Benchmark-driven implementation sequence

  1. Establish production chess/index correctness on 3–5 pieces against existing trusted WDL and distance files, including all special-move tests.
  2. Run the supplied packed-bitset and exact-FP16 microbenchmarks. Add end-to-end measurements of relation generation, ranking, transposes and boundary probing.
  3. Implement warp-per-group slider segment reductions and knight stencils, retaining a scalar legal-move fallback for every unsupported case.
  4. Generate and independently verify all six-piece material tables with complete dependencies. Record per-class elapsed time, physical I/O, peak memory and exact coverage.
  5. Demonstrate seven-piece external-memory generation with restart/duplicate-work injection. Compare hot-cache and cold-storage operation.
  6. Scale by independent material/pawn layers first, then distribute large quiet components. Same-node NVSwitch and cross-node commodity networking need distinct routing policies.
  7. Complete eight-piece dependencies before claiming general nine-piece coverage. Op2 can be an early nine-piece verification milestone but does not replace missing unrestricted subtables.

Modal GPU functions and Modal multi-node clusters can host workers; platform access and networking must be confirmed before deployment. GPU sandbox workers on other providers can use the same immutable shard protocol. Do not assume NVLink between separately scheduled workers. No remote GPU instance was launched or paid service used for this research.

10. Validation and remaining work

The supplied validation passed 120 cyclic graphs, 12,720 random-graph nodes, 22,941 duplicate notifications, a 256-edge forced chain, a radix-carry regression, three clocked-DAG cases including a 150-ply deadline/100-ply claim threshold, and 160 actual chess groups. The independent counter oracle and the floating-point fixed-point solver agree. Certificates check terminal anchors, decreasing win/loss proof ranks and defensive draw closure.

Remaining implementation risks are production indexing and symmetry boundaries, all special moves, rule compatibility, external dependency access, asynchronous distance correctness, real transactional checkpoints and hardware throughput. Only full coverage counts plus independently checked proof/distance evidence justify publishing a solved tablebase.

The best candidate is a hybrid segmented bitset / exact floating-point solver with dependency-ordered clock DP and asynchronous packed frontiers for the unclocked stage. It preserves complete coverage while letting future hardware change tile sizes and scheduling without changing game semantics.

11. Whole-collection budgets: the one-hour target remains unachieved

The per-material capacity table above is not a budget for the entire collection. NULP counts 38,176,306,877,748,245 canonical locally legal eight-piece positions, including its stated special-right conventions. This is an enumeration model, not a proof that each state requires separately stored bits or that every state is historically reachable.

Enumerating that domain in one hour requires 10.60 trillion states/s. At H100 SXM peak HBM bandwidth of 3.35 TB/s, the budget is only 0.316 physical bytes/state. A conventional dense sweep reading and writing two bits per state consumes 0.5 bytes/state and takes at least 95 minutes at peak bandwidth, before move processing or additional sweeps. This is a conditional bound for that representation, not an impossibility theorem against a symbolic algorithm.

Writing 1.5–2 PB of final output in one hour requires 417–556 GB/s at the destination. If all output crosses an assumed 64 GB/s one-direction PCIe 5 link, export alone takes 6.5–8.7 hours. CPU-side expansion can bypass that GPU link but cannot remove the final output throughput requirement. R2 provides no guarantee of this aggregate upload rate. No H100 or live R2 measurements were obtained.

Source inspection of Syzygy finds combinatorial equal-piece indexing and board/color symmetry, five WDL outcome classes in .rtbw files, and DTZ data in .rtbz files. Compression builds a hierarchical dictionary from adjacent symbol pairs and Huffman codes it, with block indexes for point queries. Entire constant domains can use a single-value marker. Capture results reconstructed during probing allow selected stored cells to become compressor-controlled fillers. Distance information can be stored for one side and reconstructed for the other.

ChessTB adds probe-time reconstruction: omit a side-to-move frame and rebuild it by one-ply minimax, or store losing distances and reconstruct winning distances from children. These choices cannot be combined arbitrarily because they can create circular dependencies. Capture/promotion bounds free some WDL cells to take compressor-friendly values; boundary markers must remain. Winning DTZ=1 cells can be omitted where a value-preserving zeroing move reconstructs them. The format uses independent LZ4-HC/dictionary WDL blocks and frequency-ranked LZMA distance blocks.

Precision qualification: ChessTB documents up-to-one-ply coarsening of cursed/blessed DTZ distances in its one-byte tier. Its reported shipping size is therefore not a guarantee of byte-for-byte equality to an arbitrary exact-distance target. Our strict-distance mode must preserve original ply values. DTM parity halving, by contrast, is lossless. Extra castling WDL+DTZ files add about 704 GiB in the reported ≤7 collection.

Research on decision DAGs, MTBDDs and logic minimization is relevant, but the ECAI paper found Syzygy most compact in its tested tables; logical representations can improve query time. These experiments start with solved labels and do not establish a shortcut for generating every eight-piece outcome.

13. Measured exact experiments and the compression direction

The new exact grouping prototype computes strong bisimulation: terminal labels agree and each member has the same set of successor groups. WDL and DTM are preserved. It passed 32 random cyclic graphs and a constructed 640-state repeated graph reducing to five groups. On complete canonical KQvK it was much less successful: 46,138 nodes including the capture draw sink became 45,249 groups, only a 1.020× reduction. It retained 606,868 of 609,873 edges. Refinement plus solving took about 1.22 s versus 0.27 s for the ordinary sparse oracle after graph construction. This is a negative result; do not adopt this grouping as the performance improvement.

All 46,137 KQvK board positions independently matched the published Syzygy WDL table. Maximum DTM was 20 plies. A domain-specific geometric WDL predictor also matched every position: a legal black queen capture or a source stalemate is drawn; otherwise the stronger side wins. This covers the tested standard KQvK board domain with a fresh clock, not arbitrary clocks or a theorem for larger materials.

A promising research direction is a deterministic outcome predictor plus an exact exception index, selecting independently per block between that representation, symbolic rules and conventional Syzygy-style codes. Lookup is predictor(position) overridden by an exception when present. Exactness requires complete certified coverage of the exceptions, not a sampled accuracy score. For illustration only, if an eight-piece outcome predictor had error fraction ε, ideal exception-location entropy plus a two-bit exception value would cost N[H₂(ε)+2ε]/8 bytes. At ε=10⁻⁴ this is about 7.98 TB; at ε=10⁻⁶ about 112 GB. These hypothetical numbers exclude model size, random-access indexes, distances and proof metadata. No such eight-piece predictor or exhaustive certification has been achieved. The difficult research problem is proving large outcome regions without enumerating their individual states; a tiny final representation alone does not solve generation.

The included r2_blocks.py implements a local research storage format: two-bit ordinary WDL, independent Zstandard pages, per-frame checksums, content-addressed grouped objects, indexed range reads, batched query grouping and an LRU cache. Default raw pages cover 262,144 positions (64 KiB); object targets are 1 GiB. A read-only S3 range adapter can be supplied an external client. This is transport/storage infrastructure, not an improvement over Syzygy compression, a fifty-move table, or a completed cloud service.

15. Actual compression improvement with a functioning chess prober

The exact adaptive codec selects per block among constant values, offset/palette packing, bit planes, lag residuals and predictor-plus-exception streams. Candidates include raw, Zstandard and LZMA encoding, and selection counts the entire frame including its 32-byte integrity header. The current TBC2 extension preserves signed 64-bit values with raw, XOR-lag and byte-plane encodings; narrow pages retain TBC1. No rounding is allowed. A narrow predictor is optional and hash-checked; every correction is stored. No eight-piece predictor has been trained or certified.

The full native KQvKR WDL streams contain 3,822,504 stored index slots, including Syzygy's compressor-selected illegal/capture-resolvable fillers. Every stored symbol round-tripped. At 65,536 cells/block, adaptive frames used 21,302 bytes versus 25,342 for the same-frame packed-Zstandard baseline, a 15.94% reduction. This initially remained larger than the published 20,496-byte file.

The earlier v2 experiment at 262,144 positions per block used 17,586 bytes, including object data, authenticated indexes, root manifest and chess metadata. The current v3 archive adds per-frame authentication and binds the chess index and rules into the catalog: 18,224 bytes, about 11.09% smaller than the published 20,496-byte KQvKR WDL file. This is one complete four-piece material, not a full four-/seven-/eight-piece set. It does not justify reducing the projected eight-piece size by this percentage.

native_wdl_bridge.py reuses python-chess's canonical ranking and capture-resolution semantics with our range-readable symbols. It does not open the original KQvKR WDL payload. It matched 2,500 legal FEN probes including color mirrors against the original Syzygy files, and matched 100 DTZ probes while still using original local DTZ data. The batch required 3 archive ranges totaling 16,776 bytes; repeating it required zero archive reads. Routing/chess metadata was already loaded. Other-material dependencies remain local. The bridge uses private python-chess interfaces pinned to chess 1.11.2.

The KQvK exact DTM experiment also verified loss-only reconstruction of all winning distances and lossless parity halving. Its full distance value stream compressed to 16,208 bytes, while parity-halved losing values used 4,724 bytes. Those numbers exclude the loss-entry index and WDL metadata, and are not complete-file savings. Reconstructing wins inspects children, so a storage reduction can raise lookup work. Keep that tradeoff explicit and batch child requests.

17. Fast lookup with fewer paid origin requests

  1. Compute routing and canonical rank locally. Cache versioned material/metric routing metadata. A production catalog needs hierarchical material/range directories, rather than loading an entire all-eight catalog or calling ListObjects per query.
  2. Page the index. Current v3 objects carry 32-byte offset/length/inline-value/checksum records; legacy v2 uses 16 bytes. A small authenticated directory hashes index pages; fetch only the relevant pages, rather than an object's full index. Index and directory caches have explicit byte budgets.
  3. Batch legal children and user positions. Discover missing symbols across the batch, read unique required blocks, then resume exact capture/minimax resolution. Never change a value because a dependency is still missing. WDL and distance requests can have different dependency waves.
  4. Merge nearby ranges. Use one contiguous GET for a cluster, capped at 1 MiB, 4 KiB gaps and 2× byte amplification in the default planner. This uses ordinary single-range requests supported by R2, not an assumed multipart-range API. Optional bounded parallel reads hide independent miss latency.
  5. Cache and deduplicate. Keep decoded hot blocks and metadata near the prober. SingleFlightStore joins concurrent identical immutable range reads and caches returned bytes. Its test collapsed 16 simultaneous callers to one underlying read and verified retry after failure.
  6. Use an edge cache for immutable ranges. range_worker.mjs supplies a read-only R2 proxy and joins identical in-flight reads. It wraps a range as its own HTTP-200 resource with a content-addressed cache key. Cloudflare's Cache API rejects direct 206 puts, is local to a data center, and does not provide tiered caching. This implementation is mock-tested, not deployed.

19. Edge cases and exact state boundaries

Current storage tests cover signed 64-bit extremes, zero-length frames, partial final pages, all codec modes, padding, decompression limits, predictor mismatches, corrupted indexes/frames, failed streaming publication, capped range reads and IDs above 253. JSON transports large integers as decimal strings; Rust parses position IDs directly into integers. The one-pass Python publisher commits its root only after immutable payload and content-addressed chess metadata have been fsynced. Source-symbol caches are bound to both source-table and cached-array checksums; corruption forces re-extraction.

The chess suite checks 400 standard/Chess960 board snapshots, 16 repetition-claim states, 2,832 WDL positions, 418 en-passant cases including 60 value-changing EP positions, all four promotions and capture promotions, and cross-material deferred dependencies. A separate 5,000-position KNNvKP sample exercises all five published WDL classes, including cursed wins and blessed losses. Sixteen concurrent batches, companion-metadata corruption, invalid query cleanup and closed sessions are tested. These are finite regression suites, not an exhaustive proof of all chess positions.

Board snapshots preserve turn, placement, promoted flags, raw EP, castling rights, Chess960 mode and counters. Game-context records preserve repetition counts and an explicit history-completeness flag. This represents the required context; it does not implement a castling tablebase or solve a full FIDE repetition-history graph. WDL archives carry the published Syzygy reset-clock semantics, and FEN alone cannot certify a complete prior history.

20. Packed lookup and stable physical ranges

The authenticated v3 path retains packed pages and extracts only queried cells. It avoids expanding an entire block to int64 and rehashing all decoded values at each lookup. Its trust contract is explicit: the publisher must fully verify decoded pages before authenticating encoded frames. Legacy v2 retains full decoded-checksum verification. Shared cache identities use immutable object hashes rather than material-local ordinals, preventing cross-material collisions.

On the local complete KPvKP archive, a synthetic 128-batch, 2,048-query uniform trace with a 128 KiB page cache and a 1 MiB compressed cache reduced Python origin reads from 1,104 to 13 using stable 16 KiB physical tiles. The compressed working set was 198,506 bytes and fit in cache. Clustered traffic sometimes transferred fewer bytes with ordinary coalesced ranges than with aligned tiles. Select alignment from measured locality; these results imply neither a full-eight hit rate nor cloud latency.

21. Rust and current NVIDIA cuTile

Rust is the production implementation target. The tested rust/ project provides an exact page encoder, selective authenticated page decoder, legacy/v3 native-ID archive reader, sorted/deduplicated batch planner, capped range reads, global byte-budget caches, aligned physical tiles, concurrent single-flight and a finite-graph WDL oracle. Its own CPU code forbids unsafe. Python remains the independent oracle and current archive publisher/FEN adapter. The Rust CLI currently probes native archive IDs; the custom v3 FEN adapter remains in Python. The newer native Rust FEN reader is described in SIX_PIECE_SPEC.md. A complete GPU generator remains to be implemented.

The Rust suite reads 402 independent Python codec fixtures covering ten modes and three compressors, rejects 3,216 encoded-frame mutations, compares 10,000 v3 and 10,000 legacy native chess IDs, tests 100 independently solved graphs, enumerates 65,536 loss-mask predicates, and joins 16 concurrent tile requests into one origin read. Reverse interoperability checks feed Rust-encoded frames back into the Python decoder. Formatting, Clippy and release tests are reproducible from bundled sources and fixtures.

A Rust cache-pressure trace of the same size reduced local origin reads from 1,355 to 13 and read 198,506 bytes with alignment; its independently checked timings are recorded in rust_cache_benchmark.json. The Rust and Python traces/cache accounting differ, so these are not a controlled language speed comparison. Local filesystem timing also excludes cloud transport and may benefit from the OS cache.

NVIDIA/cuda-rust now supplies both cuTile and cuda-oxide SIMT kernels over a shared runtime. The GPU project pins revision bc46b1ffb751885073066b087594045f07f0f81b. Use Tile for regular dense operators and evaluate SIMT for irregular move generation and frontier traffic. Upstream requires Hopper Tile IR 13.3; CUDA 13.3 is recommended in the inspected README. Our attempted GPU build stopped in cuda-bindings because no CUDA toolkit is installed. The supplied kernel is formatted but its host/JIT compilation and H100 execution remain unverified.

The Rust GPU microbenchmark validates exact 64-child bitmask predicates before timing one million synthetic resident rows. It excludes move generation, ranking, dependency traffic, compression and distance solving. Its nominal 32-byte-per-row traffic is a synthetic accounting model, not measured HBM bandwidth. More than 64 children must combine blockwise win-OR and all-winning-AND predicates. FP16/FP32 reductions are an optional bounded exact arithmetic experiment; use them only when useful shared relations and measured throughput justify them.

Frontier target remains unmet: a language/toolchain choice and fast local lookup do not demonstrate complete eight-piece generation in one hour. The package contains no complete eight-piece generator, no H100 throughput result, and no measured complete-eight compression factor. The next hardware milestone is an end-to-end small-material solve with independent published-table verification, including indexing, legal moves, promotion/EP closure, transfers, compression and durable output.
